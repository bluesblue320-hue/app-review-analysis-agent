# 阶段 5：性能、稳定性与发布

> 周期：第 6–8 周，与阶段 4 后半段并行  
> 目标：用固定数据、固定环境和可重复脚本证明系统满足性能、故障降级、重启恢复和上线回退要求。

## 1. 性能基线

### 固定夹具

创建 10,000 行中文评论夹具，要求：

- 1–5 星分布可控。
- 包含正面、负面、中性、风险、评分/情绪不一致样本。
- 包含多个版本和至少 90 天时间范围。
- 包含 UTF-8、BOM 和 GB18030 文件变体。
- 包含长文本、边界列数、PII 模式和无效行。
- 使用合成内容，不放真实个人信息。

夹具生成参数和随机种子固定，性能报告记录代码版本、Python 版本、CPU、内存、数据库版本和是否预热。

### 指标目标

| 场景 | 目标 |
| --- | --- |
| 10,000 行上传 + 解析 + 预处理 + 持久化 | 当前开发机不超过 30 秒 |
| 预热后摘要 | P95 不超过 3 秒 |
| 评论分页，limit=100 | P95 不超过 1 秒 |
| 数据集删除 | P95 不超过 3 秒，完成后不可读 |
| 规则 Agent | P95 不超过 3 秒 |
| 外部模型 Agent | 单独统计，不计入确定性 SLA；必须有总超时 |

## 2. 优化顺序

必须先测量再修改，按以下顺序：

1. 数据集读取一次，筛选一次，多个指标复用同一结果。
2. 去除不必要的 `deepcopy` 和 DataFrame ↔ JSON 往返。
3. 评论分页下推数据库，禁止先加载全部记录再切片。
4. 为真实 where/order 条件增加索引并检查查询计划。
5. 摘要按数据集、规范化筛选、算法版本和 insight ID 缓存。
6. 上传批量插入，控制事务大小；不逐行 commit。
7. 最后才评估多进程或异步化；Gate A 后端保持单 worker。

不能通过降低数据限制、减少正确性校验或关闭 PII 脱敏达到性能目标。

## 3. 性能测试场景

- 冷启动首次摘要、预热摘要、缓存过期后的摘要。
- 无筛选、窄筛选、关键词筛选、高风险 view、不一致 view。
- 1/10/25 个并发读请求。
- 上传同时进行摘要读取。
- Redis 正常、慢响应、断开。
- PostgreSQL 正常、连接池接近上限、短时重启。
- DeepSeek 快速成功、60 秒超时、429、500、非法 JSON。

每个结果至少记录 P50/P95/P99、吞吐、错误率、CPU、内存、数据库连接和 Redis 命中率。

## 4. 48 小时稳定性验证

在与生产相同的 Compose 拓扑中运行，至少覆盖：

| 时间点 | 操作 | 预期 |
| --- | --- | --- |
| T0 | 迁移、启动、上传夹具 | 所有服务 ready，数据可查询 |
| T+2h | API/前端重启 | dataset/insight 恢复，缓存可重建 |
| T+6h | 停止 Redis 15 分钟 | 服务 degraded 但摘要可计算，无数据丢失 |
| T+12h | DeepSeek 未配置 | 看板和规则 Agent 正常 |
| T+18h | 模拟模型超时/5xx | 在总超时内规则降级 |
| T+24h | 数据库备份与恢复演练 | 恢复到独立实例并通过数据校验 |
| T+30h | 制造已过期数据 | 一小时内清理，关联数据和缓存失效 |
| T+36h | 并发分页与摘要 | 无串数据、死锁或连接泄漏 |
| T+42h | 主动删除 | 所有关联数据不可访问 |
| T+48h | 收集资源与错误报告 | 无持续内存增长、无高频未知错误 |

稳定性期间使用合成数据和测试令牌，不调用真实用户评论。

## 5. 发布门

### Gate A：第 6 周 MVP

- 阶段 0–2 全部退出条件通过。
- 阶段 4 的 Streamlit Gate A 完成。
- 10,000 行性能目标通过。
- 48 小时稳定性验证通过。
- 生产环境变量、备份、恢复和回滚均完成演练。

### Gate B：第 8 周增强版

- LangChain 与 Direct Adapter 均为 46/46。
- Redis 故障降级和缓存一致性测试通过。
- Next.js Playwright 核心旅程通过。
- 新前端灰度观察期没有 P1/P0 问题。

## 6. 发布流程

1. 冻结 release candidate，记录镜像 digest、迁移 revision 和前端版本。
2. 在空数据库执行迁移和 Compose 健康检查。
3. 从最近备份恢复到临时环境，执行兼容性测试。
4. 部署数据库迁移，再部署 API，最后切换前端。
5. 执行登录、上传、摘要、分页、Agent、删除的生产冒烟。
6. 观察错误率、P95、数据库连接、Redis 命中和 Agent 降级率。
7. 达到观察窗口后标记发布完成，并保存验收报告。

## 7. 回滚策略

### 应用回滚

- 前端可独立切回 Streamlit。
- Agent provider 可切回 `direct` 或完全禁用外部模型。
- Redis 缓存可通过配置关闭。
- API 镜像可回滚到兼容当前数据库 schema 的上一版本。

### 数据库回滚

- 优先使用向前修复 migration。
- 破坏性迁移前必须备份并验证恢复。
- 不在生产自动执行 Alembic downgrade。
- 若新应用无法使用旧 schema，保持旧应用运行并从备份恢复到独立数据库，确认后再切换。

## 9. 最终退出条件

- 所有质量、安全、数据和性能指标都有可重复的命令或报告，不以人工口头确认代替。
- 发布和回滚过程至少演练一次。
- 已知限制写入 README/运维手册，DeepSeek 可选和单实例边界清晰。
- 48 小时期间无数据丢失、跨数据集串读、令牌泄露、持续内存增长或无法解释的高频 5xx。
